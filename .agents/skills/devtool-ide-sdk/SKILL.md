# devtool ide-sdk Workflow

Set up VS Code (or shell-script) cross-debugging for an OpenEmbedded/Yocto recipe against a running target device.

## Prerequisites

The OE build environment must be sourced before running any `devtool` commands:

```bash
cd /path/to/poky-workspace
. build/init-build-env
```

`build/init-build-env` is generated by `bitbake-setup` and lives in the workspace's `build/` directory.

## Full Workflow

### Step 1 — Check out recipe source with debug build

```bash
devtool modify --debug-build <recipe>
# e.g. devtool modify --debug-build cmake-example
```

Source lands in `build/workspace/sources/<recipe>/`.

### Step 1b — Image debug settings (automatic)

`devtool ide-sdk` automatically writes the required debug settings to the image's workspace bbappend before the bitbake build. No manual `local.conf` edits are needed. The following settings are written to `build/workspace/appends/<image>.bbappend`:

```bitbake
# devtool ide-sdk: image debug settings
IMAGE_GEN_DEBUGFS = "1"
IMAGE_FSTYPES_DEBUGFS = ""
IMAGE_CLASSES += "image-combined-dbg"
IMAGE_INSTALL:append = " gdbserver"   # or lldb-server for clang recipes
IMAGE_INSTALL:append = " <recipe>"
IMAGE_INSTALL:append = " <recipe>-ptest"  # only if the recipe has ptest
```

If these settings were previously added to `local.conf` manually, remove them to avoid duplication.

### Step 1c — Choose QEMU networking mode

If no target IP was provided, ask the user which QEMU networking mode to use — this determines the flags for `devtool ide-sdk` in the next step:

| Mode | ide-sdk flags | Requirement |
|------|--------------|-------------|
| **slirp** | `-t root@localhost -P 2222` | No sudo needed; debug ports are auto-forwarded via QB_SLIRP_OPT |
| **TAP** | `-t root@192.168.7.2` | Requires sudo/root on host |

Prefer slirp when possible. `devtool ide-sdk` always writes `QB_SLIRP_OPT` to the image bbappend with all 4 debug port forwards (2222/SSH, 2323/telnet, 1234/gdbserver, 1235/gdbserver alt) and forces `do_write_qemuboot_conf` to regenerate `qemuboot.conf`, so any `runqemu ... slirp` invocation picks them up regardless of which `-t`/`-P` flags were used.

**Do not start QEMU yet.** `devtool ide-sdk` builds the image first; QEMU is started after (Step 2a).

### Step 2 — Generate IDE configuration

`devtool ide-sdk` builds the sysroot and image, deploys the recipe, and writes VS Code config files into the source tree. Run it before starting QEMU:

```bash
# slirp (preferred — debug ports auto-forwarded via QB_SLIRP_OPT):
devtool ide-sdk <recipe> <image> -t root@localhost -P 2222 -c [--ide=code|none]
# e.g. devtool ide-sdk cmake-example oe-selftest-image -t root@localhost -P 2222 -c --ide=code

# TAP (requires sudo on host):
devtool ide-sdk <recipe> <image> -t root@192.168.7.2 -c [--ide=code|none]
```

Always pass `-c` (`--no-host-check`) when targeting QEMU — the SSH host key changes on every boot.

`devtool ide-sdk` always writes `QB_SLIRP_OPT` with all 4 debug port forwards to the image bbappend and runs `bitbake <image> -c write_qemuboot_conf --force` so `runqemu slirp` picks them up immediately.

To regenerate only the IDE config files without re-running bitbake (e.g. after changing the target IP or port):

```bash
devtool ide-sdk <recipe> <image> -t root@<target-ip> [-P <port>] -c --skip-bitbake [--ide=code|none]
```

### Step 2a — Start QEMU

Once `devtool ide-sdk` has built the image, start QEMU from the workspace root (build env must be sourced):

```bash
# slirp with nographic (runs in background / dedicated terminal):
cd /path/to/poky-workspace && . build/init-build-env build && runqemu <image> snapshot slirp nographic

# slirp with SDL window:
cd /path/to/poky-workspace && . build/init-build-env build && runqemu <image> snapshot slirp

# TAP (requires sudo):
cd /path/to/poky-workspace && . build/init-build-env build && runqemu <image> snapshot
```

With `QB_SLIRP_OPT` written by `devtool ide-sdk`, `runqemu slirp` forwards all 4 ports:
```
Port forward: hostfwd=tcp:127.0.0.1:2222-:22 hostfwd=tcp:127.0.0.1:2323-:23
              hostfwd=tcp:127.0.0.1:1234-:1234 hostfwd=tcp:127.0.0.1:1235-:1235
```

**`nographic` note**: QEMU uses stdin/stdout for the serial console. Run it in a dedicated terminal that stays open — closing the terminal kills QEMU.

**Stale lock file issue**: If QEMU processes are killed without clean shutdown, lock files at `/tmp/qemu-port-locks/` may remain, causing `runqemu` to bump ports (e.g., 2222 → 2224). Fix:
```bash
rm -f /tmp/qemu-port-locks/*.lock
```
Then restart QEMU. Verify it got port 2222 by checking the `runqemu - INFO - Port forward:` line in the output.

### Step 2b — Generate a Copilot skill in the recipe source tree

After `devtool ide-sdk` succeeds, read the generated config files to discover the exact names of the cmake preset, deploy task, and launch configurations, then create `.agents/skills/<recipe>-remote-debug/SKILL.md` in the source tree.

Use these commands to extract the names:

```bash
grep -E '"label"|"name"' \
  build/workspace/sources/<recipe>/.vscode/tasks.json \
  build/workspace/sources/<recipe>/.vscode/launch.json \
  build/workspace/sources/<recipe>/CMakeUserPresets.json
```

Then create the skill file at `build/workspace/sources/<recipe>/.agents/skills/<recipe>-remote-debug/SKILL.md` with:

- **Description** — one-line summary referencing the recipe name, cmake preset, and target
- **Step 1** — Install recommended extensions (`ms-vscode.cmake-tools`, `ms-vscode.cpptools`)
- **Step 2** — Select the cmake configure preset (exact name from `CMakeUserPresets.json`)
- **Step 3** — Run the deploy task (exact label from `tasks.json`)
- **Step 4** — Launch configs table: name, binary, mode (`once`/`attach`), behaviour — using the exact names from `launch.json`
- **Regenerate section** — the full `devtool ide-sdk ... --skip-bitbake` command with the actual target/port used

### Step 3 — Open VS Code (ide=code, default)

Use the absolute path (substitute the actual workspace root and recipe name):

```bash
code /path/to/poky-workspace/build/workspace/sources/<recipe>/
```

VS Code opens with the generated `.vscode/` configuration. Follow the steps below inside that window.

#### 3a — Install recommended extensions

When VS Code opens it will prompt to install recommended extensions. Accept, or install manually:

- `ms-vscode.cpptools` — C/C++ IntelliSense and GDB integration
- `ms-vscode.cmake-tools` — CMake build integration and preset support

#### 3b — Select the cross-compile CMake preset

Open the Command Palette (`Ctrl+Shift+P`) → **CMake: Select Configure Preset** → choose the OE preset (named after the recipe/machine, e.g. `cmake-example-cortexa57`). This preset is defined in `CMakeUserPresets.json` and points CMake at the OE sysroot and cross-compiler.

Then run **CMake: Configure** to configure the build.

#### 3c — Build and deploy

Use the **Terminal → Run Task** menu and select:

```
install && deploy-target <recipe>: <arch>
```

This cross-compiles the recipe and deploys the result to the target over SSH.

Alternatively, trigger a build via **CMake: Build** (`F7`), then run the deploy task separately.

#### 3d — Start a debug session

Open the **Run and Debug** panel (`Ctrl+Shift+D`). Three launch configurations are generated per binary:

| Config suffix | Behaviour |
|---------------|-----------|
| `_once` | `preLaunchTask` SSHes to target and starts `gdbserver --once :<port> <binary>`. GDB connects, server exits after the session. |
| `_attach` | `preLaunchTask` attaches `gdbserver` to an already-running process (by `pidof`). |
| *(clang)* | Uses `lldb-server platform` in MULTI mode; server is started once and reused. |

Select a configuration and press **F5**. The `preLaunchTask` starts the debug server on the target automatically before GDB/LLDB connects.

### Step 3 — Use shell scripts (ide=none)

Generated scripts live in `build/workspace/sources/<recipe>/oe-scripts/`:

```bash
# Start lldb-server (MULTI mode) on target
./oe-scripts/lldb_server_<port>_<binary>_multi start

# Launch lldb on host, connected to target
./oe-scripts/lldb_<port>_<binary>

# Stop server
./oe-scripts/lldb_server_<port>_<binary>_multi stop
```

For GDB (`ide=none`), the analogous `gdbserver_*` and `gdb_*` scripts are generated.

### Step 4 — Cleanup

```bash
devtool reset <recipe>
```

## Toolchain Variants

| Recipe `TOOLCHAIN` | Debugger | launch.json type | Server |
|--------------------|----------|-----------------|--------|
| (default / gcc) | GDB | `cppdbg`, `MIMode: gdb` | `gdbserver` |
| `clang` | LLDB | `lldb`, `CodeLLDB` extension | `lldb-server platform` |

- Default recipes (no explicit `TOOLCHAIN`) use GDB.
- Clang recipes (`TOOLCHAIN = "clang"`) use LLDB via the CodeLLDB VS Code extension.

## Generated Files (ide=code)

| File | Purpose |
|------|---------|
| `.vscode/launch.json` | Debug configurations (one per binary × mode) |
| `.vscode/tasks.json` | preLaunchTask / postDebugTask SSH commands to start/stop debug server |
| `.vscode/settings.json` | cmake preset, cmake kit path |
| `.vscode/c_cpp_properties.json` | IntelliSense include paths |
| `.vscode/extensions.json` | Recommended extensions (ms-vscode.cpptools or CodeLLDB) |
| `CMakeUserPresets.json` | Cross-compilation cmake preset |

## Debug Server Modes

| Mode | Behaviour |
|------|-----------|
| `once` | Server exits after one session (simple, default for GDB) |
| `attach` | GDB attaches to already-running process |
| `multi` | Server persists, serves multiple sessions (LLDB default) |

LLDB MULTI mode: server is started via `preLaunchTask`, stays alive between sessions, stopped by `postDebugTask`.

## Important Warnings

| Warning | Meaning | Fix |
|---------|---------|-----|
| `gdbserver not installed in image` | Image lacks `gdbserver` package | Should not appear — `devtool ide-sdk` writes this automatically. If seen, rerun `devtool ide-sdk`. |
| `lldb-server not installed in image` | Image lacks `lldb-server` package | Should not appear — `devtool ide-sdk` writes this automatically. If seen, rerun `devtool ide-sdk`. |
| `IMAGE_CLASSES += "image-combined-dbg" is missing` | No rootfs-dbg, debug symbols won't be found | Should not appear — `devtool ide-sdk` writes this automatically. If seen, rerun `devtool ide-sdk`. |
| `IMAGE_GEN_DEBUGFS is not enabled` | Source file mapping for GDB/LLDB will be absent | Should not appear — `devtool ide-sdk` writes this automatically. If seen, rerun `devtool ide-sdk`. |
| `Some source directories ... are not included` | Intermediate build dirs excluded from debug search | Informational; source stepping still works for srctree |

## For Best Debug Symbol Experience

`devtool ide-sdk` automatically writes `IMAGE_GEN_DEBUGFS = "1"`, `IMAGE_FSTYPES_DEBUGFS = ""`, and `IMAGE_CLASSES += "image-combined-dbg"` to the image's workspace bbappend before the build. No `local.conf` changes are needed.
